## 2. 公共安装与引用

在已有完整地图、编辑模式使用`XingHai → COM-01 → 安装到当前完整地图`。安装器要求本场景恰好一份InventorySession/InventoryView、原双角色协调器、完整目录和NPC样板；缺失或已安装时明确拒绝，不覆盖旧模块。不要在用户dirty场或原始基底反复执行安装。

安装器集中配置`CommerceService.inventory/inventoryView/userInterface`、`merchants`、`merchantCatalog`、`worldContainers`与唯一`InventoryInteraction`的Commerce接线。运行时不让每个商人全局寻找另一个库存或保存服务。

作者工具创建场景实例和目录资产；新商人引用共享目录、配置独立实例ID后进入本地图服务登记，无需商人专属买卖代码。`PF_Merchant.prefab`已有实际落图并登记的NPC实例，女主个人店仍引用原玩家Prefab。`final-prefab-diagnostics.json`已验证重复身份和缺ID/目录明确拒绝，保留原身份，不自动改ID；这不表示任意Prefab拖进场景后无需配置即可交易。

Prefab作者流程：

1. 将对应COM模板Prefab放入目标地图，例如`Assets/OSSASTRA/Commerce/Prefabs/PF_Merchant.prefab`。
2. 明确配置独立实例ID和商品目录；箱子同时配置所属map。复制出的已有非空ID不能与原实例共用。
3. 执行COM-01的Register（登记）菜单，把所选实例接入目标`CommerceService`，检查诊断后保存该地图。工具显式登记，不靠运行时全局寻找引用；漏配/重复拒绝后修正，再登记成功。

## 3. 三种身份不要混用

| 字段 | 表示什么 | 配置方法 |
|---|---|---|
| `MerchantDefinitionSO.definitionId` | 商品目录模板，例如`sample-general`。 | 同模板多店共享，只保存不可变作者配置。 |
| `MerchantShop.instanceId` | 一家店的稳定实例，例如`merchant:com01-general-a`。 | 场景落图时持久保存；A/B不能共用同ID。 |
| `CommerceWorldContainer.instanceId`与`mapId` | 一个逻辑世界箱及所属地图。 | 不用名字、坐标或Unity临时InstanceID代替。 |
| `CommerceService.profileId` | 一份经济档案。 | 验证档与正式档分别命名，不通过删除旧文件“重新开始”。 |
| 保存`sessionId` | 本次加载代际。 | 服务每次启动生成新值，旧请求/旧写入不得覆盖新会话。 |

`MerchantShop`和箱子代理的OnValidate仅对场景内、ID为空的新实例填入ID；不会在OnEnable生成、不会改变已有非空ID。**复制已有实例会连同非空ID复制，不能假定自动获得新身份**；必须在编辑阶段明确配置新ID并保存。重复身份应报错，禁止运行时偷偷改旧ID来规避存档冲突。已存档实体的ID或所属目录更改属于数据迁移，不能直接改名后宣称旧状态仍等价。

当前队伍通过两个角色已序列化`ActorId`恢复四个手槽；角色集合、必需容器几何和owner不匹配时拒绝启用，不猜测名字相同就是同一个角色。

## 4. 商店目录、价格和刷新

创建菜单：`Assets → Create → OSSASTRA → Commerce → 商店目录`。每个`MerchantGoodsConfig`配置实际ItemDefinitionSO、`buyPrice`、`sellPrice`、`targetStock`与`allowZeroPrice`。

- `buyPrice=-1`不售卖；`sellPrice=-1`不收购。未配置不得变成免费物品。
- 零价仅在`allowZeroPrice=true`时合法；数量为正整数，价格乘法按受检整数计算。
- `targetStock`是补货目标量；每家店拥有独立运行库存和revision，不能运行时改共享SO当库存。
- `refreshSeconds`是可保存的模拟时间间隔；重开面板/启用商人不补满，关闭游戏期间不按现实时间补货。
- 当前SAMPLE安装器使用可调示例价格`10+3n / 4+n`；这是本轮测试政策，**不宣称与原型16钱币食品/100钱币卖价逐项相同或平衡已经完成**。

付款从同一账本按团队包→安全栏→当前合法可访问后备扣实体`trade-coin`。够钱仍须试算最终容量；扣空币堆腾位可交货时允许成功，最终不能完整交货则整笔拒绝。出售针对所选实例/数量，装备中、预留、拒收或返款无法放入团队包时拒绝。售出物为明确交易消耗，不自动加回货架/回购；拖到货架不视为出售。

目录或物品定义改变可能使定义指纹变化。旧档指纹不匹配会拒绝加载，不自动丢弃旧物/重播种；正式作者改表需要另走兼容迁移或使用明确的新验证profile。

## 7. 保存位置、状态与失败

`CommerceService.saveDirectory`留空时使用`Application.persistentDataPath/Commerce`；显式填写时使用该目录。具体主文件由只读`SavePath`查看，形式为`economy-<profileId的SHA256>.comsave`，并有`.bak`、`.session`、`.write.lock`及短暂`.tmp`文件。

正式发布两场使用`commerce-main`和默认目录。以下是取证期间使用的隔离验证档，不是当前发布配置：

```text
profileId: com01-integration-proof-v2
saveDirectory: E:/WORLDCREATOR/XingHaiHuiLang/work/OSSASTRA/COM01-20261028/profile-v2
```

以上为`schema2-restored-live.json`及正常买卖证据使用的隔离档；早期schema1验证档保留，没有按空档覆盖。重进Play证据与后来真正Editor重启证据分别记录；当前发布配置由`final-assets-published-config.json`确认。

### 7.1 schema分层

| 层 | 当前版本 | 含义 |
|---|---|---|
| 文件封套 | `OCS1`、封套schema 1 | 档案/会话身份、修订/序号、载荷schema、指纹、长度及SHA256完整性。 |
| `CommerceSaveSnapshot.PayloadSchema` / `CommerceRuntimeSnapshot.schema` | 2 / 2 | 使用保留null的生产Codec，避免普通物品被编码为默认装备。 |
| `CommerceEconomySnapshot.schema` / `InventoryRuntimeState.schema` | 1 / 1 | 内层经济及库存宿主各自的字段合同；它们仍为1不代表当前文件退回旧编码。 |

schema2为当前生产载荷格式，未知/旧载荷不能自动当新档授予。文件封套完整、Codec可解码、当前配置兼容是不同校验层，不能用其中一项替代全部恢复校验。

初始化先建立定义/基本容器，完整验证候选经济和宿主字段；只有主档明确`Missing`才授予团队/装备初值。普通世界箱按稳定ID首次注册原子授予整箱，搜空或重开不补满。坏档、未知版本、缺定义、重复ID或手槽错位都不能落回默认播种。

成交先完整提交内存再请求保存；普通字段/模拟时间变化也会标脏并经检查点保存。`stateRevision`、`saveSequence`、`persistedRevision`分别表示当前经济版本、快照次序、落盘版本；较旧A保存完成不能把较新B标成已保存。

写失败时内存成交不反做、不重新扣币，旧有效主档保留。界面显示失败与“重试保存”；限制新商店成交和主动库存编辑，但原先已受理的合法消费/全灭继续发生并成为待保存的新版本。恢复介质/权限后按重试保存最新内存；不要通过重复点击购买来代替保存重试。正常退出会尝试排空保存，失败明确记录诊断，不承诺未落盘数据断电不丢。

实际文件拒写的UI回放已验证：保存失败时确认按钮自动禁用并显示无有效报价；解除拒写、点击重试后显示“已保存”，原选择/数量1保留，按钮恢复可用，币274不因重试而再次扣除。受控关闭夹具也已验证最后一次主线程变更在Disable/Destroy及Inventory先失活时写入、协调器`IsClosed=true`；这属于实际宿主生命周期测试，不等同完整Editor进程退出/重启。

Commerce单根禁用的边界已定向修正：保存正常时，禁用Commerce后原库存编辑仍可用，恢复启用后也可编辑；真实Move已通过。禁用期间不运行Update中的3秒自动检查点，Destroy/退出仍采集最终状态并flush；文件保存失败门继续有效，不因禁用而绕过。单根OnDestroy只释放自己安装的编辑gate。证据`disable-boundary-red.json`→`disable-boundary-green.json`，不把禁用贸易模块等同关闭原背包。

### 7.2 显式检查与恢复备份

坏主档不会自动选择备份。Editor入口为`Tools → XingHai → Commerce → 备份检查与显式恢复`；这是作者恢复工具，不是游戏内玩家菜单。除41项文件层回归外，已通过Editor窗口公开口对隔离档实际检查、显式恢复，并在随后重进Play时通过原完整启动门、恢复Ready。实际GUI确认框的人工物理点击不在此证据范围。

1. 退出Play并等待当前保存结束，在`Assets/OSSASTRA/`自有场景中选中实际`CommerceService`。
2. 打开上述窗口，点击“读取当前选中对象”或“检查当前对象主档与备份”。核对场景、profile、实际目录、主档和备份源路径、Payload schema、StateRevision、SaveSequence及文件记录指纹。
3. 窗口只检查文件完整性、Codec/schema及文件内外修订/指纹一致性，**不会在此证明当前物品定义、角色、箱子和引用兼容**。基础检查失败时不能恢复。
4. 点击“明确恢复这份已检查备份”，在确认框再次核对来源与版本后确认。提交时在同一写锁内重验整份冻结预览；过期预览拒绝。原主档保留为`.corrupt-*`，成功后显示实际保留路径，并写新保存代际，防止旧后台writer盖回恢复结果。
5. 窗口不自动进入Play、重载或播种。之后正常启动，由原启动门完整验证候选定义、唯一归属、角色手槽、箱/掉落及引用；失败仍拒绝启用并保留文件，不能以恢复按钮返回成功代替该层校验。

恢复预览只能确认一次，失败或目标profile/目录改变后需重新检查。窗口公开验收口为`Inspect(service)`与`RestoreInspectedBackup(true)`；它们遵守相同EditMode、自有场景与预览校验要求。

本次隔离恢复回执为`backup-editor-restored.json`：主档StateRevision/SaveSequence为14/15，明确选择的备份为13/14，恢复结果为13/14，原主档保留为回执中的完整`.corrupt-*`路径；`backup-restored-runtime.json`证明随后正常启动Ready。新运行会继续递增修订/序号，不要求运行中的计数永远停在恢复版本。

## 8. 多地图与内容边界
