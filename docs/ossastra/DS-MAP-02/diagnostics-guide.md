# DS-MAP-02 闪烁诊断操作

诊断默认关闭。正常试玩不会自动写逐帧文件；只有点击导出按钮才写JSON。当前已修复确认的研究场共面深度渲染缺陷，修复后实际源网格的固定快照回归稳定；**用户全部动态或独立装备闪烁仍未据此宣布闭环**。

## 打开研究场

从Unity菜单 `Tools/OSSASTRA/地图研究/打开双角色战斗样地` 打开已保存的 `Assets/OSSASTRA/Scenes/Research/SC_DontStarvePartyCombatLab.unity`，进入Play。诊断面板位于底部遭遇重置面板上方，不替换正式HUD。

研究场和角色依赖本机已有素材；此文档不包含这些媒体。不要把旧单人样地、双角色样地同时叠加运行，以免出现两套研究会话。

最新首次生成双角色样地的builder会装配诊断面板。若自建研究副本没有面板，应由该场的装配者明确添加 `Ossastra.MapResearchIntegration.Diagnostics.MapFlickerTraceRecorder` 和 `MapFlickerTracePanel`：Recorder的 `map` 指向本场MapResearchRoot，`actors` 指向要记录的真实角色，Panel的 `recorder` 指向该Recorder。记录器不会扫描或接管其它场景。

研究深度修复由独立的 `MapResearchSpineDepth` 组件承担，已装于新样地3个Renderer实例及已有研究Variant的1个身体。它在真实网格完成事件修正负间距的bounds，不是诊断开始按钮的副作用，也不需要打开追踪才能生效。正式基础Prefab、Spine第三方代码与Shader没有因此改写。

## 捕捉一次异常

1. 确认角色存活、Game窗口获得焦点，点击 **开始追踪**。这次开始会清空上一轮内存记录与标记；需要的旧记录应先导出。
2. 按原方式旋转、移动或使用动作，观察用户所指的具体局部。不要同时跑切控自动故事与独立身份验收夹具。
3. 看到异常后点击 **标记异常并导出**，先保留最近的有界记录。面板显示本机文件路径或失败原因。
4. 若还需要异常之后的片段，可继续短暂采样再点击 **停止追踪**，随后再次点击 **标记异常并导出**。第二份文件含较后的记录与两次标记；每次使用新文件名，不覆盖第一份。

**停止追踪**会精确退订本记录器的事件并保留现有内存数据。停止、标记、导出都不是暂停功能，世界与已受理动作继续运行。面板使用原输入端口登记自身指针区域，禁用时只释放本面板owner，避免点击按钮同时攻击。

退出Play、销毁记录器或再次开始都会影响内存保留；需要交接的记录请在退出前导出。开始后若样本始终为0，先确认身体仍在实际生成网格；0条记录本身不能证明闪烁或渲染故障。

相机阶段会跳过已销毁的角色或身体，不把其旧摘要追加成新帧记录。替换角色或身体后，仍应停止、重新配置对象后再开始；记录器不会自动追踪新实例。对于尚存活的身体，相机阶段可能沿用最近的网格摘要，应核对 `meshFrame`，不能把相机事件帧当成新的身体网格。

## Inspector的补充入口

选择场内Recorder，可使用 **仅标记当前异常（不写盘）**、**手动导出最近记录** 或 **选择本机文件夹并导出**。仅标记后继续一小段再停止、导出，能够保留同一个标记前后的上下文。组件右键菜单也提供备用入口。

可配置项：

| 配置 | 意义 |
| --- | --- |
| `map` / `actors` | 明确的研究镜头和角色集合；应停止后再改对象 |
| `capacity` | 每次开始分配的固定样本条数，默认2048，限制1至4096 |
| `markerLabel` | 标记说明；保留最新32个标记，每个最多160字符 |
| `exportDirectory` | 手动导出目录；留空使用默认本机目录 |
| Panel的 `left` / `bottomOffset` / `width` | 仅调整研究诊断面板位置和宽度 |

容量是**记录条数**，不是帧数或固定秒数。一个身体每帧可能记录网格、相机开始、相机结束多条。以两个身体、每身体每帧三条和60fps举例，2048条约覆盖5.7秒；实际覆盖时长由真实回调频率决定，Editor高帧率时会更短。溢出只覆盖最旧记录，不增长内存；Inspector显示覆盖数量。

默认导出位置为 `Application.persistentDataPath/OSSASTRA/MapResearchDiagnostics/`，文件名形如 `DS02-trace-时间-唯一标识.json`。面板显示实际路径，Inspector可选中复制。无需提前创建目录。记录与本机录像保持在本机，不随原作素材公开上传。

## 怎样理解报告

| 字段或状态 | 正确解读 |
| --- | --- |
| `UNREPRODUCED_CPU_TRACE` | 没有触发当前CPU摘要候选判定；不等于屏幕没有局部闪烁。当前全顶点统计含未被三角索引引用的尾部容量，不能据此排除实际绘制部分全零alpha |
| `CPU_EMPTY_OR_ZERO_ALPHA_CANDIDATE` | 出现相应CPU摘要候选，需要和画面、动作及生命周期核对；不是自动根因判定 |
| `gpuVisibilityVerified=false` | 固定边界：本记录器不证明GPU可见性、局部正确性或遮挡通过 |
| `frame` / `meshFrame` / `provenance` | 当前事件帧、最近网格生成帧与采样阶段；相机记录可能沿用较早网格摘要 |
| `expectedCameraId` / `renderCameraId` | 期望研究镜头与实际触发相机回调的实例；网格阶段的后者为0 |
| `actorId` / 身体及网格实例字段 | 区分两人、不同身体和网格双缓冲；不能只凭Actor名字混合记录 |
| `currentActorId` / `controlRevision` | 原party协调者的采样快照；原单人场显式标 `single` / -1，并非诊断另建Current |
| `actionId` / `phaseId` | 相位只关联仍活动且身份吻合的动作；idle相位应为空 |
| `samplingError` | 采样器自身读取错误，应先检查此项，不能直接解释为游戏故障 |

`cpuCandidates`是本轮累计数；环形记录覆盖最旧条目后，早先候选的明细可能已不在当前导出窗口。请及时标记导出，不要仅凭累计数判断异常发生在哪一帧。

当前候选集合只取正式身体控制器的Skeleton，独立装备Spine不会混入身体记录。汇总alpha与bounds不能证明每个slot或装备部件正确。交接异常时，应同时给出标记JSON、尽量连续的录像、具体部位、角色、装备、动作、镜头方位与复现步骤。

本轮诊断合同已隔离实测20/20通过，证明默认关闭、有界存储、真实回调、身份/相位关联及停止退订等功能。销毁身体的实际Play回归另有8/8通过：旧实例新帧样本0，重新绑定真实存活身体后停止，继续3次相机事件仍不增长记录。这些合同没有验证“用户全部局部/装备闪烁已修复”。当前调查证据与GPU夹具限制见 [flicker-investigation.md](flicker-investigation.md)。

修复前证据为 `gpu-fresh-results.json` 中唯一版本的 `PartialFlickerGpuProbe`：同一正式姿态、网格等价检查通过，375个顶点容量实际引用308个。0间距在相机微小偏移下最多5,124/22,558个内部像素差值达到32，独立快照改为-0.0001间距后该计数为0，重复0偏移逐像素相同。早期拓扑检查失败及第三次运行被导入/域重载打断的结果均不列为有效A/B。

修复后证据 `gpu-fixed-results.json` 为 `MODEL_SNAPSHOT_STABLE`：实际源间距-0.0001、实际bounds Z extents约+0.0017，严格引用网格等价检查通过，六个相机偏移的两组最高阈值差异计数均0。这一轮两组都读取已修正源条件，属于回归；不等于用户全部动态/独立装备通过。夹具固定的 `productionFixApplied=false` 表示它自身不应用修复，实际安装以安装回执、`sourceHadNonzeroSpacing`、实际源配置与bounds为准。
