# 统一保存与失败恢复契约（拟定）

这是一份给 Unity 实施的目标政策；**不是** Duckov 或当前 Three.js 已具备同样保证的描述。原作有 `StockShop_<merchantID>`、`EconomyData`、`PlayerStorage`、`PlayerStorage_Buffer` 等独立保存键，`ES3.StoreCachedFile` 是后续落盘入口；本轮没有证明跨键原子性或重启恢复。Three.js 当前原型刷新不存档。Unity OSSASTRA 当前 `InventorySession.Start` 重新播种，没有玩法 Save/Load。证据见[鸭科夫](evidence/duckov-static.md)、[原型](evidence/threejs-current.md)、[Unity](evidence/unity-current.md)。

## 唯一快照与生命周期

一份 `CommerceSnapshot`（版本 1）应包含同一逻辑时点的如下数据；不得分别把币新值和背包旧值写成可见存档：

| 数据域 | 必须保存 | 权威与恢复原则 |
| --- | --- | --- |
| 库存 | 已注册定义的稳定 ID/版本引用；全部实例 ID、定义 ID、数量、容器 ID、坐标、装备 payload 的物品部分（耐久/能力必要状态）；容器形状、owner、revision。 | 从 `InventoryLedger` 一次采样；装备仍由既有装备模块在绑定后读取同一 payload，不能另造角色装备真相。 |
| 实体币 | `trade-coin` 的所有实例、数量和所在容器；允许支付的容器集合。 | 币仍是上行库存实例。`Economy.gold` 或独立 Wallet 不另存同笔余额。 |
| 商店 | 稳定 `merchantInstanceId`、静态目录 ID/版本、每条货架当前数、限购/锁定状态、下次或上次刷新时间与计时基准。 | 模板 ID ≠ 场景实例 ID。复制两个 Prefab 时显式不同 ID；若需要共享店铺，则配置独立共享组 ID。 |
| 世界 | 地面包/搜寻容器的稳定逻辑 ID、地图 ID、位置、已搜/已领取状态与实例对应；手动掉落跨图政策。 | 物品存在于 Ledger 容器；世界代理是从记录重建的显示，不是第二份数量。跨图清理应依用户决定，不能沿 Three.js 原型的暂态政策悄悄删存档物品。 |
| UI 以外的选择 | 快捷栏/优先定义等与库存对应的引用；芙蕾个人商店已确认的有限解锁/对话标记。 | 无效引用在加载校验时处理并报告；不把整套关系/剧情系统纳入本模块。输入焦点、窗口开合、未确认交易草稿不保存。 |
| 幂等与未完成动作 | 需要跨保存重放保护的最近请求 ID/结果摘要；已提交事务序号。 | 未提交预留和正在拖拽意图不当作成交恢复；加载后重建或取消，防止重复结算。当前 Ledger 的 `requests/wipes/reservations` 只在内存，应决定并实现恢复边界。 |

加载顺序：校验版本/校验和/定义目录与实例 ID → 创建容器与实例的**完整候选 Ledger** → 校验数量、堆叠、格位、装备 payload 与归属、商人 ID 唯一性 → 装入商店及世界记录 → 原子切换当前会话 → 绑定装备投影与创建世界代理 → 发一次完整刷新事件。若存档不存在，**只首次**按场景初始授予播种；若存档存在但损坏，不回退到初始授予并覆盖它。现有 `InventorySession.Start:60–83` 必须因此改为“恢复或播种”分支，且绑定顺序不能读到半成品。

## 成交、保存与用户反馈

1. **预览**只读快照和报价：记录角色/商人身份、物品实例/数量、报价、Ledger/店铺 revision、访问代际与请求 ID。UI 预览不能扣币。
2. **确认时**重新验证距离/视线/活性、会话、货架、价格、币、空间和装备资格；在候选 Ledger + 店铺状态上计算，全部通过才以一个内存提交更新。`CommittedInMemory` 表示商品/币/货架在本会话一致；重复请求返回同一结果或明确拒绝，不能再执行一次。
3. **保存时**从该提交后的同一时点采样完整 `CommerceSnapshot`，先写临时文件并校验，再原子替换当前快照，保留上一份有效备份。此文件方案须在实际存储介质/平台上验证替换语义；若接入现有全局存档，则注册为同一提交参与者，而不是并行写第二份物品数据。
4. **反馈**区分 `Rejected`（无变化）、`CommittedInMemory / SavePending`、`Saved`、`SaveFailedButInMemory`。写盘失败不能告知“已永久保存”；当前会话继续保留一致交易状态，保留上一份有效存档并允许重试。若用户退出时仍失败，明确提示本次交易可能在重启后回到上一快照；不向旧快照补写半笔经济。

此政策选取“内存成交立即可见，保存失败单独提示”。若产品要求“写盘成功才算成交”，需把确认改成持久化先行或事务日志的另一合同，不可只改提示文案。断电/进程杀死后最多恢复最近一份完整有效快照；不承诺没成功落盘的内存交易一定存在。

## 失败矩阵与恢复门

| 场景 | 提交/恢复结果 | 验证故事 |
| --- | --- | --- |
| 缺钱、无空间、拒售、数量越界、报价或修订变化、超距/遮挡、角色死亡/切人 | `Rejected`；玩家物、币、货架和地面记录都不变。 | 记录前后完整快照哈希与失败原因；独立刷新可另生新 revision。 |
| 连点购买/卖出、重复拾取、事件重放 | 同一请求只结算一次；新请求须再次验证当前版本。 | 用同一 request ID 提交两次并重载后再重放，数量守恒。 |
| 拆分/合堆/整理期间又交易 | 旧计划因 revision/access 变化拒绝；排序结果不会复活卖出物。 | 在排序计算后先成交，再提交旧排序计划。 |
| 交易候选计算中异常 | 还未切换当前 Ledger/店铺状态，原账本不变；错误可追溯。 | 注入定义缺失或货架更新失败，核对前后值。 |
| 写临时文件/替换失败 | 当前会话仍是完整内存状态，旧快照保持可加载，UI 标 `SaveFailedButInMemory`。 | 注入磁盘拒写/中断；重启加载旧完整快照，无半笔币/货物。 |
| 文件损坏、版本未知、定义缺失、重复实例/商人 ID | 拒绝装载并保留原文件/备份；若备份有效，经明确恢复流程使用备份，记录诊断。 | 不自动播种、清空或吞掉未知物品；测试含两个相同模板商人。 |
| 代理创建失败 | 逻辑物品仍有唯一地面容器或提交前整笔拒绝；有明确重建/提示路径。 | 杀掉显示 Prefab，确认没有双持有或无归属物。 |

## 需要确认的产品边界

- `trade-coin` 默认允许从团队包/安全栏/后备扣款，与现行 Three.js 一致；Unity `CanAccessContainer` 目前只在后备持有人存活时可访问。若玩家希望仅随身币或现金/账户双渠道，需重新定义支付范围和验收。
- 手动丢弃跨图是否保留、商人补货采用游戏内时间还是现实时间、芙蕾个人货架是否提供商品及独立库存，均影响快照字段/测试；当前静态证据不能代替用户玩法决定。
- 选用项目现有全局存储还是模块独立文件，要在实施前复查是否已有新存档入口；本轮静态检索没有找到，第三方插件存在不构成已接入。
