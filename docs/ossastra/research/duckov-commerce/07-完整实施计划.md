# OSSASTRA 物品、交易与交互闭环 Implementation Plan

**Goal:** 在已完成一次公共安装的 OSSASTRA 正常地图中，摆放已配置商人 Prefab，使用现有角色走近完成芙蕾对话/个人商店、普通商人买卖、物品取放/整理，并在重启后恢复同一经济状态。

**Architecture:** `InventoryLedger` 继续独占物品/实体币/装备 payload 的数量与位置；纯 Commerce 核心持商店货架和报价，用一个事务协调边界准备并提交 Ledger 与货架状态。Unity 宿主只供角色/距离/输入捕获/世界代理，UI 只读快照并发送命令。版本化模块快照统一保存库存、币、商店及地面记录。

**Tech stack:** 本机 Tuanjie `2022.3.62t16` / Editor `1.10.4`；Input System `1.14.4-t1`；uGUI `1.0.0`；Unity Test Framework `1.1.33`；现有 `Ossastra.CharacterCore.asmdef` 为无引擎引用纯程序集。版本来自本机 `ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`，实施前复核。

**Spec:** [三方对照](02-三方功能对照.csv)、[调用链](03-交易与物品调用链.md)、[UI 契约](04-UI布局与交互契约.md)、[根结构](05-Unity依赖与根结构建议.md)、[保存契约](06-持久化与失败恢复契约.md)。用户 ZIP 的总纲是需求草稿，以上本机证据和用户后续决定优先。

## 全局约束与决定点

- 代码/资源分别放 `Assets/OSSASTRA/Scripts` 与 `Assets/OSSASTRA/Commerce`；不迁入第三方 DLL、反编译完整代码、原作媒体或真实存档。
- 不改角色控制算法、朝向、动画、美术模型、音频；用现有角色身份、位置与 `SetInventoryCapture`/`SetInputCapture`。必须改公开接线时先列具体文件和原因。
- 当前 Unity 恰好两角色 `InventorySession` 是既有宿主硬条件；商人不是第 3 名玩家角色。场景、Prefab、SO 只用 Unity MCP/Editor API 修改；保护当前 dirty 场景与输入资产。实施前重新读 `AGENTS.md` 和任务登记，由唯一 Unity writer 占用路径。
- 先保持实体 `trade-coin` 为唯一交易货币，默认从当前可访问的团队/安全/后备容器付款。若用户选择账户余额，应另写一次性转换与防双计方案。
- **D1 个人商店**：芙蕾货架现在为空，首次实现需要她可配置且可买卖的目录；具体上货、收购范围、解锁条件由用户确认。未确认前可用醒目标注的测试目录验证机制，不能交付成最终角色内容。
- **D2 世界生命周期**：手动掉落跨地图是否保存、商人刷新使用游戏内或现实时间、搜空箱状态是否纳入首次闭环，均会改变快照与体验。计划默认“保存跨图地物、模拟游戏时间刷新、保存已搜空状态”，需在评审时确认。
- **D3 成交/存档**：计划采用“内存一致成交立即可见，统一快照随后落盘；失败明确提示且保留上一完整快照”，详见 [保存契约](06-持久化与失败恢复契约.md)。如果要求落盘成功才反馈成交，必须在写交易前换合同。
- **D4 UI 参照**：已有原型源码和 1440×900 背包/商店/芙蕾菜单三张实画面；原作真实几何未取证。若目标是对原作的精确布局验收，需要 [缺屏清单](04-UI布局与交互契约.md#确切缺失的参考画面)；在取得之前，不能以“高度还原鸭科夫”判 PASS。

上述决定点不要求用户对每个内部里程碑重复批准；它们在开始正式实现前一次审阅。用户授权实施后，可连续推进 I1–I6；遇到与决定点相反的新要求再调整。COM-00 本轮停在计划交付。

| `Assets/OSSASTRA/Tests/EditMode/Commerce/*`、`PlayMode/Commerce/*`（新增） | 对原子失败、整理/保存/多商人、正常输入路线做有判定力的测试。 | Test Framework；具体 asmdef 引用在 I1 编译门确定。 |

**拟议纯接口**（不是现有 API，I1 锁定签名后所有后续任务沿用）：

```csharp
TradeQuote Quote(TradeRequest request, CommerceAccessSnapshot access);
TradeResult TryCommit(TradeRequest request, CommerceAccessSnapshot access);
InventoryBatchResult TryPrepareBatch(InventoryBatchCommand command, out PreparedInventoryBatch prepared);
void CommitPreparedBatch(PreparedInventoryBatch prepared, bool notify);
CommerceSnapshot CaptureConsistentSnapshot();
LoadResult RestoreOrSeed(CommerceSnapshot saved, InitialSeed seed);
```

`TradeRequest` 至少带 `RequestId`、`ActorId`、`MerchantInstanceId`、`Side`、指定 `ItemInstanceId`/`DefinitionId`、正整数 `Quantity`、报价版本、Ledger/货架 revision 和访问代际。`TradeQuote` 带单价、总价、可付容器、当前库存与失败原因；预览不授权。`TradeResult` 区分拒绝、内存提交和保存状态。候选批次将扣币、发物/取物、容量/装备限制和 ID 更新在 Ledger 副本中验证；商店货架也先得候选副本。提交阶段只执行经验证的无异常字段切换，通知在两者切换后发；事件回调异常不得变成半笔。具体签名可随 I1 的编译事实微调，但所有权与事务边界不能变。

## I1：冻结合同与最小编译骨架

**交付**：能在无角色模型/音频的 EditMode 测试中创建 Ledger、店铺状态和价目，并编译通过；没有业务行为或第二库存。

- [ ] 重读 Unity `AGENTS.md`、`OSSASTRA_RULES.md`、sync 登记/当前 `git status`；记录要改的 dirty 文件是否被其他 writer 占用。冻结 `trade-coin` 容器、D1–D4 决定、商人 ID 规则和首次地图安装方式。
- [ ] 新建纯 Commerce asmdef 与最小 Contracts；`CommerceCore → CharacterCore` 单向引用，运行时 `ItemDefinitionSO` 只在外侧冻结。执行一次 Editor 编译，确认本机 Tuanjie 对类型/程序集的实际支持。
- [ ] 先写 EditMode 失败测试：同一商人模板的两实例 ID 不相同、负价/数量溢出拒绝、`trade-coin` 数量仅来源于 Ledger、无配置目录时明确诊断；运行目标测试应先失败，再做最小实现并复跑。
- [ ] 交付 Review Gate：接口图、精确文件 diff、编译结果、上述测试通过；不要先碰用户 dirty 场景。

## I2：物品批次、交易、整理与世界取放

**交付**：纯规则支持买入/卖出/拒绝、已有转移/拆合堆和可取消整理；失败前后库存、币、货架数完全一致。

- [ ] 在 `InventoryLedger` 先加测试：币有足额但收货无空间、货架售罄、拒售、同一 RequestId 连交两次、旧 revision/访问代际、价格溢出、装备 payload 资格、卖价钱币无处存放；对每例断言 Ledger 完整快照与货架 revision 都不变。再实现 `TryPrepareBatch/CommitPreparedBatch` 及交易协调器。
- [ ] 明确买入报价绑定**指定店铺实例**、商品定义和数量；卖出绑定**指定物品实例**。出售输入上限先取该实例数量，避免原型用同定义总数量设上限却只卖一个实例的矛盾。当前正常 UI 是单项直接出售；`sellBatch` 的历史函数不自动变成验收项。
- [ ] 在候选 Ledger 中完成叠堆/拆分/交换/商店收付款；提交前重验当前角色/商人/容器资格、余额、货架、容量、修订，拒绝时不触发 Changed。交易后的刷新是独立事件与 revision，不假装属于被拒交易。
- [ ] 保留 Unity `InventoryView` 已接的团队/外箱整理及 `Ledger.PlanSort/CommitSort`；以原型四态为质量目标补充“找到可行但未证明最优/取消/不可行”的可读结果，允许有界算法而非移植 Worker。测试整理中发生交易/消费后旧计划拒绝、数量/装备 payload/位置守恒；标注可行与最优的证据边界。
- [ ] 世界拾取/丢弃沿现有 `InventorySession.Drop`、`InventoryInteraction`，增加稳定逻辑 ID 与代理重建政策；测试非法落点、重复拾取、满包、代理创建失败及补偿/恢复。手动掉落跨图政策按 D2 冻结，不复刻原型的暂时清除而又要求存档保留。
- [ ] Review Gate：纯核心无 UnityEngine 依赖；对失败注入与守恒用例通过；场景中旧背包/装备操作定向回归通过。

## I3：统一保存与恢复

**交付**：一个版本化快照恢复币、物、商人货架与地面状态，文件失败不产生部分经济状态。

- [ ] 先写 Save/Load 失败测试：交易后重启、新商人和同模板双商人、丢弃再拾回、搜空状态、装备 payload ID/耐久、快捷引用、坏文件、缺定义、重复实例/商人 ID、旧版本和中途拒写。测试必须比较整份领域状态，不只检查 UI 文本。
- [ ] 给 `InventorySession.Start` 建恢复或播种的唯一分支：先注册定义/容器，校验并构造完整候选 Ledger+店铺+世界记录，成功后绑定装备与代理；新档只播种一次，坏档不播种覆盖。
- [ ] 在 `CommerceSaveAdapter` 使用 `Application.persistentDataPath` 下独立模块目录的临时文件、完整校验和备份；选定序列化器与原子替换手段后在本机平台实测。若实施时发现工程已有正式全局存档入口，改为注册同一次快照参与者，不同时保留第二份物品存档。
- [ ] 实施 `CommittedInMemory/SavePending/Saved/SaveFailedButInMemory` 的事件/提示；保存失败保留内存状态及上一份有效文件，可重试，退出前清楚提示。重启最多恢复最近完整有效快照，不凭空补回未落盘交易。
- [ ] Review Gate：杀进程/拒写/损坏注入、双商人重启、装备身份和所有币容器一致；无真实用户存档参与验证。

## I4：芙蕾、商人、背包 UI 与单一交互

**交付**：正常键鼠/手柄输入下，六类 [UI 状态卡](04-UI布局与交互契约.md#六类状态卡)可从正式入口走通；对话和商店都绑定原实体身份。

- [ ] 先写 PlayMode/浏览器等价交互测试：同一 F 只开一个目标，商店 F 不触发拾取，数字框聚焦时 WASD/F 不漏世界，Esc 从数字框→商店→背包退栈，失焦/死亡/换控/换场释放**本窗口**捕获，关闭同次按键不触发攻击。
- [ ] 在现有 `InventoryInteraction` 加商人/芙蕾能力仲裁，使用 `NpcRoot` 身份和既有 `SetInventoryCapture`；不新增第二个键盘监听或修改角色行为策略。对话 SAMPLE 经配置保留；个人商店用同一芙蕾 ID，目录按 D1 决定。送礼/角色装备菜单若仍不在范围，显示明确不可用，不冒充已实现。
- [ ] 组合现有 `InventoryView` 与新的 CommerceUIRoot，而非再造全套背包：普通/贸易布局、选货/选物、详情、数量、成功/拒绝/保存状态、Ctrl 快移、拖拽取消、团队与外箱整理。购买/出售确认始终调用纯服务重验，按钮灰显不是授权。
- [ ] 用当前原型矩形作第一版 Unity 对照，分别截现用桌面分辨率与一档窄屏；检查区域相交、网格滚动、提示位置、焦点和拖拽命中。如果取得原作/PPT画面，再只调整视觉和布局，不改领域交易规则。验收分“功能输入可用”和“原作视觉对照”，分别签结论。
- [ ] Review Gate：从正常 UI 完成芙蕾对话/个人商店和普通买卖，错误状态可读；Unity PlayMode 录像/截图附版本与分辨率，角色/音频范围外 diff 为零。

## I5：Prefab 落图与地图安装

**交付**：独立验证场和至少一张正常地图都能从现有角色走到新放商人买卖；复制商人模板无需写地图专属交易代码。

- [ ] 用 Unity MCP/Editor API 创建 `MerchantShop` 配置/Prefab、UI 组合、地面代理和验证场；模板可换静态目录、视觉和交互范围。编辑器校验必填引用、重复稳定实例 ID、缺定义和未安装公共服务，给明确错误。
- [ ] 公共安装仅做一次：绑定既有 `InventorySession`、单一 F 仲裁、CommerceService、UI、保存目录与商人注册；新地图首次安装清单写明依赖。之后复制已配置 Prefab、设置目录/位置/稳定实例 ID 即可交互；同模板两份库存独立。
- [ ] 正常地图用**真实现有角色控制**靠近商人→买→整理→丢/拾→卖→保存/重启；不能用开发 IMGUI 按钮或测试直接调用替代。另在无角色模型/无音频的独立场用模拟端口验证纯核心，证明可拔插边界。
- [ ] Review Gate：列出真实地图、Prefab/场景 GUID、配置步骤和录屏；已 dirty 场景没有被覆盖或无关合并。

- [ ] 审查每个生产 diff：角色控制、动作、朝向、动画、模型、音频无无关改动；商店/UI无第二库存/钱包；资源引用和 asmdef 无循环。按项目同步协议登记/释放 Unity writer。
