# 交易与物品调用链

COM-00 定向源码/IL 对账，2026-10-28。Three.js 以 `Origin@bb969cc88591fd8e93e4c939cb52719dd652a948` 为准；鸭科夫以本轮复核的 Core/ItemStats DLL 指纹与 MethodDef token 为准；OSSASTRA Unity 以 `Project_ANKALUTE@f0e41a6ce9a6e66b0afd8a01d4e83dda1e3e830e` 的本机工作树为准。这里的“调用链”表示源码/IL 中可见的调用与写入顺序，**不代表本轮已实测买卖成功路径或异常可达性**。原型的背包/商店/芙蕾菜单另有[定向浏览器画面](evidence/prototype-ui-observation.md)；它没有提交交易。其他证据分别在 [Three.js 现行审计](evidence/threejs-current.md)、[鸭科夫交易与物品静态证据](evidence/duckov-static.md)、[鸭科夫 UI 静态证据](evidence/duckov-ui-static.md)、[Unity 当前审计](evidence/unity-current.md)。

## 买入：资格、扣款、交货、货架写入

### Three.js 当前普通商人

`backpack-panel.ts:40,44–46` 选货生成 `shopQuote` → `merchant-shop.ts:10–13` 的 `buyFromShop` 重新检查商人可访问、世界/访问代际/控制角色、货架 revision、数量和报价 → 从团队/安全/后备中筛出合法实体钱币并检查总量 → 在库存草稿中扣钱币 → `addInventoryItem(draft,'team',...)` 检查并放入所购商品 → 成功后写回 `m.items/containers/serial`，再减 `shop.stock[definitionId]`、增加 `shop.revision`。若团队包放不下商品，方法在这些业务写回之前返回“未扣钱或库存”；若报价或身份已变也拒绝。`ensureShop` 可按模拟时间刷新 SAMPLE 货架并提高 revision，因此“拒绝交易”不等于整个世界对象绝无任何时间驱动变化。**这是同一次页面运行中的同步内存提交，不是跨刷新/断电事务。** 货架为 `'empty'` 的芙蕾茜娅个人商店可打开，但当前不能从她的货架买商品。[原型证据](evidence/threejs-current.md)

### 鸭科夫普通商店 UI

`StockShopView.OnInteractionButtonClicked`（Core `0x06001DAA`）→ UI `BuyTask` 状态机（Core `0x06002C5A/IL_002C–002D`）向 `StockShop.Buy` 固定传数量 **1** → `StockShop.<BuyTask>d__58.MoveNext`（Core `0x06002C4D`）依次检查 Entry/库存与报价 → `EconomyManager.Pay` 扣账户/允许的现金来源 → **异步**创建物品 → 标注 `UI_Trade` 来源 → 送主角包；送包返回 false 时尝试 `PlayerStorage.Push` 或地面掉落 → 最后写 `Entry.currentStock = old - amount`，通知并返回 true。满包在这条方法中不是直接拒单条件。`StockShop.<Buy>d__57` 有 Busy/`buying` 门；异常时释放和 UI 回执尚不能从已扫描 IL 完整确认。[交易 IL](evidence/duckov-static.md)、[UI IL](evidence/duckov-ui-static.md)

该 IL 顺序明确显示付款早于异步建物、交货和货架扣减；本方法未见显式补偿分支。异步实例化、仓库兜底、落地代理、保存失败在正常内容中是否可达，以及失败后实际归属，**未运行验证**。底层 `BuyTask` 接受数量参数，但当前普通 UI 固定单件；不能把其他入口或数量大于 1 的可达性写成玩家已遇到的问题。[交易 IL](evidence/duckov-static.md)

### OSSASTRA Unity 当前

没有买入 UI/商店调用链。`InventorySession.Start` 注册定义、建立固定团队/安全/后备/外部/手槽并播种；`InventoryLedger.Grant` 能单独试算后提交一个赠予，`Transfer` 能单独提交一次转移。它们都没有商人身份、报价、实体钱币扣减、货架扣减组成的共同提交点。后续实现应把“资格与报价复核 → 扣钱并交货 → 货架修订”作为**一个**可验证业务提交，而不是串行调用 `Grant` 与 `Transfer` 后声称原子。此句是迁移设计要求，不是当前能力。[Unity 审计](evidence/unity-current.md)

## 背包转移、拆堆、合堆与整理

### Three.js 原型

`backpack-panel.ts:28,38,54,61–62` 提供选择、数量输入、拖放与预览；`inventory-operations.ts:31–39` 的 `queryInventoryTransfer` 重验世界、控制、访问代际、来源/目标容器、同层距离/视线和装备动作，再交 `queryInventoryMove` 在副本上试算。确认时 `commitInventoryMove` **再次**查询，`inventory-model.ts:22–35` 在克隆上执行放置、拆分、合堆或交换，成功才写回；失败保留原库存。数量空白表示整堆，显式正数可拆；装备只允许单件且有归属/手别约束。成功后的 UI/会话还同步装备投影、清空地面容器和失效快捷引用。[原型证据](evidence/threejs-current.md)

一键整理是独立链：`backpack-panel.ts:69–78` 取容器快照和 revision → Worker 运行 `solveInventoryPack`，超时有短预算本地回退、可取消 → `inventory-pack-commit.ts:3–5` 仅对 `optimal` 或 `feasible_unproven` 的合法结果，复核 revision、类型数量守恒、装备身份和坐标，再一次提交。`cancelled`、`infeasible`、过期 revision 不提交；`feasible_unproven` 只代表合法摆放，没有最优证明。现行 UI 可达团队包和外部箱整理。没有物品旋转/容器套娃。[原型证据](evidence/threejs-current.md)

### 鸭科夫

`InventoryEntry.OnDrop`（Core `0x060022D5`）可进入 `SplitDialogue`、`Item.Detach`、`Inventory.AddAt` 或 `Item.Combine`；`InventoryDisplay.OnSortButtonClicked`（Core `0x060022A2`）在可编辑、目标有效且未 Loading 时调 `Inventory.Sort()`。这里只证明 UI 入口，不推断排序最优性、取消语义或所有拖放失败的归属。[UI IL](evidence/duckov-ui-static.md)

ItemStats 的 `Inventory.AddAt/RemoveAt` 写内容格位和 `Item.inInventory`，`Item.Combine` 写两件的 `StackCount`，源计数归零可脱离/销毁。`Item.<Split>d__249.MoveNext`（`0x0600028F`）**先减少原堆数量，再异步创建新物**；创建失败返回 null 的分支中方法内未见恢复原数，但调用方补偿和失败可达性还没有完成验证。`AddAndMerge` 的一处调用丢弃 `AddAt` bool 是静态一致性调查点，不称已复现玩家丢物。[交易/物品 IL](evidence/duckov-static.md)

### OSSASTRA Unity 当前

`InventoryView` 的数量字段、拖放和整理按钮接 `InventorySession.Move` / `InventoryLedger.Transfer`；`Transfer` 通过 `Plan/Query` 的修订、访问代际、容量、锁与装备条件，在副本上试算并对**单次库存命令** `Commit`。Unity 当前确有整理：`InventoryView.cs:85,111,188–189` 调 `Ledger.PlanSort(id,4000)` → `CommitSort`；`InventoryLedger.cs:158–194` 在计划副本合堆、有限预算寻可行布局，提交时复核 revision、访问代际、数量与装备 payload 引用及布局。界面文案明确“可行布局，未证明最优”。这可以复用为基底，但其有界求解/状态接口与 Three.js Worker 的四态合同不同，迁移时要逐项决定/验收。[Unity 审计](evidence/unity-current.md)

## 地面拾取、主动丢弃与满包去向

| 系统 | 从输入到写入 | 失败/生命周期 |
|---|---|---|
| Three.js | 物品拖到合法地面时 `dropInventoryItem` 检查物品来源、角色动作、地面同层/可见，先建临时 `drop:manual:*` 容器，再通过 `commitInventoryMove` 转出；失败删除新建空容器，成功才把容器坐标改到目标点。F 的优先级是角色菜单 → 最近手动掉落物拾取 → 普通容器；拾取以 `commitInventoryMove(...,'team')` 回包。 | 手动掉落在地图切换被清除；与双人全灭的专用掉落包不同。拾取失败给反馈且不提交该次转移。都仅属于页面内世界状态。见 [原型证据](evidence/threejs-current.md)。 |
| 鸭科夫 | `InteractablePickup.OnInteractStart` → `CharacterMainControl.PickupItem` → `CharacterItemControl.PickupItem` → `SendToPlayerCharacterInventory` → `AddAndMerge` → `Inventory.AddAt`；`ItemExtensions.Drop` 先 `Detach`，再 `CreatePickupAgent`。商店买入送包失败还可转 `PlayerStorage.Push`，后者可能入主仓或进 `PlayerStorage_Buffer`，不能只检查背包就判断交货丢失。 | 拾取链中 `AddAndMerge` 对 `AddAt` bool 的处理和落地代理创建失败后的归属有静态疑点，未运行复现。UI 的 LootView 另有“取尽/存尽”入口及关闭时取消活动拆分对话的逻辑。见 [交易 IL](evidence/duckov-static.md)、[UI IL](evidence/duckov-ui-static.md)。 |

## 跨阶段失败与持久化对账

| 检查点 | Three.js 当前原型 | 鸭科夫静态所见 | Unity 当前/迁移需满足 |
|---|---|---|---|
| 报价或访问变更 | 买卖重新检查身份、世界/访问代际、修订与价格；拒绝旧请求。 | 商店 UI 显示可交易状态；业务方法另检库存/Busy/可售，但具体所有 UI 时序待运行。 | 库存有 `AccessGeneration`/revision；商人身份和报价 token 尚不存在。 |
| 付款后交货失败 | 购买在草稿同时容纳扣币和入物，空间失败不提交贸易；仅内存。 | `Pay` 在异步建物和投递前；未见本方法内显式补偿。投递可走包、仓、地面；异常可达性未证实。 | 需设计一次提交的扣币＋物品＋货架，或有可恢复的事务协议。 |
| 销货后返款失败 | 卖出在同一草稿中扣实例并加钱币，钱币容量失败不提交。 | `Detach/DestroyTree` 在 `Cost.Return`/`EconomyManager.Add` 之前；账户 Add bool 被忽略。真实故障未证实。 | 需定义货币容量/溢出和售出物去向；当前无售卖命令。 |
| 排序中访问变化 | 提交复核 revision；取消/不可行不提交。 | 仅确认 Sort UI 入口；内部状态/并发合同未完成研究。 | 已有计划/提交复核；不是原型 Worker 四态的同构实现。 |
| 重开与落盘 | 页面刷新无存档；手动掉落跨地图清除。 | 有独立商店、账户、仓库/buffer/物品树保存键，`CollectSaveData`/`ES3.StoreCachedFile`；不证明每笔交易当场持久化或跨键原子。 | `InventorySession.Start` 重新播种，未发现玩法 Save/Load；完整迁移必须先定义快照及失败恢复，不能把重播初始物当恢复。 |

因此后续 COM 实施的硬验收应同时观察**余额/实体币、商品实例、货架库存、容器位置、装备 payload、地面物和重开后状态**；每个失败注入点要证明总量守恒、无重复提交和明确回执。鸭科夫的局部 IL 只提供参考风险与交互结构，不能替代 OSSASTRA 自己的事务合同。具体持久化方案与故障矩阵另见 [06-持久化与失败恢复契约](06-持久化与失败恢复契约.md)。
