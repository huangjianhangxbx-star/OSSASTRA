# OSSASTRA 代码规范｜中文注释与可审查性

> **拟入库路径：** `docs/ossastra/代码规范.md`。这是本轮**待由Codex实际写入**的正文，不表示当前GitHub已经创建。若本机已存在正式代码规范，选择唯一原文件合并并从规则索引链接，禁止两个互相冲突的规范。
>
> **用户明确新增的原则（2026-10-19）：** 以后每个自有脚本，开头有中文功能大致总结；关键部分配中文解释；修改脚本时同步更新受影响注释。

## 1. 适用范围

- 立即适用于 `Assets/OSSASTRA/Scripts/**/*.cs` 的**新脚本及本轮修改脚本**。本轮对现有所有 OSSASTRA 自有生产与开发辅助脚本做**一次性开头注释补齐**，避免「以后」规则只要求新文件。
- 未来扩展至 OSSASTRA 自有 `Editor`、测试源文件以及其他自建 `.cs`。提交/改写这些脚本时遵守同样要求；测试脚本仍可用较短说明。
- 不包括 `Assets/旧代码/Script`、商业插件、Unity/Spine包内第三方源码、生成的代码、外部导入源码；不改写用户旧脚本，仅研究。
- 旧 C# 代码库中没有触及的其他文件不做全量格式化或批量更名，避免为补注释制造无关变更。

## 2. 每个脚本开头的中文功能总览（必须）

每份适用的 `.cs` 在 `using` 或 `namespace` 前放置一个精简、与代码一致的文件级注释。推荐：

```csharp
/*
 * 脚本：CharacterRoot
 * 功能：组织单个角色的子系统初始化与每帧动作执行顺序。
 * 负责：汇总输入意图、请求动作、推进动作事实、调度移动与表现。
 * 不负责：具体按键绑定、物理命中筛选、伤害数值最终写入、开发测试GUI。
 * 协作：ICharacterInputSource → CharacterRoot → 动作运行时／运动／朝向／表现。
 * 关键约束：每角色状态独立；表现不能反向判定实际命中。
 */
```

**上面只是写法示意**：Codex必须依据当前真实 `CharacterRoot.cs` 修改字段和协作关系，不得把旧描述粘贴进已重构源码。脚本本身命名是否合理仍由用户审查。

至少写清：**这个脚本是干什么的、拥有哪些职责、不应该负责什么、和谁通信、重要边界**。短工具脚本可压缩为3～5行，复杂模块可稍长，不能空泛写「处理角色逻辑」或大段复制任务计划。

## 3. 关键部分中文解释（必须，但非逐行废话）

对以下**非显而易见**的业务语义加中文行注释或 `/// <summary>`：

1. 控制权或状态的唯一写入者、Root→接口→具体组件的交接条件。
2. 输入有效性、按下边沿、Held重武装、失焦、禁启、暂停恢复等时序；说明**为何**避免重复攻击，而非描述 `if` 表面行为。
3. `ActionFact`的Accepted/Released/Ready/Cancelled/Finished之间的区别；释放事实如何进入世界命中及独立HP结算。
4. 同帧切换两角色时避免旧输入继续消费的关键顺序；已接受动作能否继续推进与切换行为的区别。
5. ActorId、DataBus、姿态/攻击方向、场景层输入配置/Prefab绑定等责任边界。
6. 任何刻意绕开直观写法的保护、生命周期清理与兼容处理，说明约束和原因。

给公共接口/公共复杂方法优先用 XML文档注释，使IDE悬停可读：

```csharp
/// <summary>
/// 接收角色的一个移动指令；只执行实际位移，不自行决定攻击朝向。
/// </summary>
public void Tick(bool allowed, float delta) { /* ... */ }
```

`CharacterContracts.cs`可以集中放同领域若干小接口；**每个接口有自己的中文职责摘要**，但不需要为了“一接口一文件”而机械拆分。私有的复杂控制分支优先加普通中文注释。

## 4. 注释与代码同步属于同一修改（强制）

- 修改脚本**职责、通信方向、状态所有者、公开接口、时序顺序、输入规则、边界条件**时，必须在**同一代码Diff**中修改开头总结与对应关键注释。
- 只改数值、局部样式或小bug，如果注释语义未变，不应为了形式任意改写。报告中标注「检查过，现有注释仍然准确」。
- 删除/移动/更名脚本时更新文件开头的真实名称、引用示意、接口说明及相关审查文件；避免注释长期停在旧路径。
- **注释不是事实来源的替代品**：如注释与代码冲突，按实际代码修正；不能修改代码强行迎合过时注释，更不能把尚未实现的功能写成已完成。
- 在任务交接中增加「中文注释核对」：列出每个新/修改 `.cs`、文件头是否存在、关键逻辑是否注释、是否因改动同步修订、是否存在待审不一致。
- 用户逐行审查时，注释本身也可以修改和推翻；审核结论只对当时提交版本有效。

## 5. 可读性与命名

- 服从根`OSSASTRA_RULES.md`：脚本/类型 PascalCase；字段/参数/局部变量 camelCase；输入使用 Inspector 配置的 Unity 新Input System；角色状态各有唯一写入者。
- 关键业务流程避免将多种动作揉成一条超长语句。中文注释帮助理解，但不能代替合理分层和清晰名称。
- 优先说明「为什么、何时、由谁调用和状态如何变化」，不为每一条普通赋值/花括号添加机械注释，不追求注释行数指标。
- 不因增加注释而引入接口、协程、外部依赖或额外运行时代码。

## 6. Codex验收流程

1. 读取适用代码规范、现行规则及本次相关真实脚本。
2. 只为新/改脚本和本轮一次性补齐范围写准确中文注释。
3. 完成实现后，从**修改后的最终源码**复核注释，不从过期设计文档生成幻觉说明。
4. 出具 `docs/ossastra/代码注释检查记录.md` 或写入本次任务审查文档（推荐后者，避免常态建立多份流水账）：文件清单、注释覆盖、已解释关键行为、待用户争议点。
5. 注释验收不等于逻辑验证；两者均通过，才可按OSSASTRA已授权的GitHub发布规则发布**候选**。
